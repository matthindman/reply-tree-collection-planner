# Reply Tree Collection Planner

An interactive page for thinking through how to collect the largest reply trees on X. Move a control
and the plan, its cost and its biases update at once. The page opens on "Best guess for
Japanese X today" (about 12% of replies in conversations of 100+ posts); the other scenarios are one click away.

## Two views

- **Cascades** (the page opens here): a root with its replies, quotes and retweets. A plan has three
  steps: search with floors on a root's own retweet and reply counts; read the replies of the roots that
  look large enough, to size the cascade; collect in two tiers (every post; replies and quotes). The
  population is `src/cascade_tables.js`: 10,000 synthetic cascades of 100+ posts, with sizes at 24, 48, 72
  and 168 hours, replies and quotes. No row is a real cascade: rows are simulated from summary statistics
  (counts, totals and histograms) of groups of at least 100 real cascades in 30 daily summaries for
  September 2026, and reproduce the measured counts and post totals by size to within about 1%. Each
  row's class (root-led or reply-led) and its root's own counts come from fitted models. The page opens
  on a plan that takes every post of cascades of 10,000+ posts and the replies and quotes of cascades
  down to 100 posts (82.5M units of the 90M left after the reserve; this reach dates from the eighth
  version, 24 November 2026). It collects a random 2% of the reply-led cascades (a sample checked on X
  is automated advertising) and a random 2% of prize draws ("follow and repost to win"; the eighth
  version opened on 20%, the largest share offered that fits, at 89.7M units; 2% again since the
  ninth version, the same day), both drawn by root ID, and searches by the root's retweet count (100+) or reply count
  (100+), which finds 77% of the cascades of 100 to 9,999 posts; a slider sets each share, from none
  to all. Which rows are prize draws comes from a topic study's shares by size. Since the sixth
  version (24 November 2026) a reply-led root is recognised from its counts (more than
  five replies for each retweet), not taken as known: one that the rule misses has its replies read
  before it is dropped, one that it wrongly flags is set aside unless sampled, and one draw is made for
  each root (`recog` in `plan()`; `'class'` gives the earlier arithmetic). The page
  also shows how much of each sampled class the sample can reach (`reach()`): the sample is drawn from
  the roots search returns, about a quarter of all reply-led cascades. Since the seventh version
  (24 November 2026) the retweets and replies on an original-post root are drawn together, from
  histograms of the two days with every post on file in groups of 100+ cascades; before, the three root
  counts were drawn independently and 10% of ordinary roots looked reply-led where 4 to 5% was measured
  (now 6%; these figures are for floors of 300 retweets or 100 replies, the seventh version's opening plan, which cost 62.9M units). One known gap against the two measured days at those floors: the rows gave
  0.54M units a month for reply-led roots read before they are recognised where those days give about
  1.4M to 2.9M. The reach among reply-led cascades of 300 to 999 posts is near 40% on this page and 26%
  on the two measured days (roots of 2 and 3 September); that is a difference between those days and the 30 files (roots of 25 August to 23 September), not an
  error in the rows, as the sixth version's text had it. The table is
  generated outside this folder and is not meant to be edited by hand. The arithmetic is `src/cascade_model.js`, the view
  `src/cascades.js` (defaults in `DEFAULTS`), checked by `node test/test_cascade.js`.
  The measured cascades themselves are confidential and are not in this repository; only aggregate
  figures and the synthetic table are.
- **Reply trees**: the reply part of a cascade, simulated from the stochastic reply-tree model (everything
  described below).

## Files

- `index.html` — the whole tool in one file. Open it in a browser, or serve it from GitHub Pages.
- `planner.html` — the same page without the HTML skeleton, for publishing as a Claude artifact.
- `src/app.js` — controls, wording and charts. **Defaults, presets and labels are in `CONFIG` and `GROUPS` at the top.**
- `src/sim.js` — the stochastic reply-tree model (18 parameters), ported from the project's Python generator.
  Runs in a Web Worker when a model control moves.
- `src/cost.js` — what each collection strategy costs and finds.
- `src/ref_tables.js` — the two reference populations (Japan 2011 simulation, US archives), binned.
  Generated by `data/export_tables.py`.
- `src/scenario_tables.js` — the precomputed scenarios (best guess, low end, high end, more quiet-root,
  more root-driven, and two fitted to the September 2026 archive: popular roots, and under quotes). Generated by `data/make_scenarios.js` from `data/scenarios.json`.
- `data/compare_presets.js` — simulates parameter sets and prints comparable statistics.
- `data/calibrate_today.js` — tunes a full parameter set to a list of targets (not used for the current best guess).
- `src/style.css`, `src/page.html` — styles and page markup.
- `test/` — checks of the simulator and the cost engine against the Python results.
- `estimation/` — Python code that estimates the model's 18 parameters from post records by maximum
  likelihood, with tests and a worked example. See `estimation/README.md`. In the public repository this
  folder holds the package itself; here it holds the README and the example, and `sync_public.sh` adds the
  package from the research repository.

## Scenarios

The buttons at the top of the left rail load a whole population in one click. They are listed in
`CONFIG.scenarios` in `src/app.js`; `CONFIG.startScenario` names the one the page opens on.
Their populations are defined in `data/scenarios.json`:

- `today` — "Best guess for Japanese X today": GPT Pro's 18-parameter preset.
- `opus` — "More root-driven": the Opus agent's preset.
- `low`, `high` — the best guess with the "Roots in the popular group" control solved so that 3.4% and 32%
  of replies sit in conversations of 100+ posts.
- `quiet` — the best guess with "Difference between conversations" raised.

To change one, edit `data/scenarios.json`, then run `node data/make_scenarios.js && python3 build.py`
(under a minute). The analyses behind the presets are kept in the project's private research repository.

## Making a change

1. Edit a file in `src/` (most changes are in `CONFIG` or `GROUPS` in `src/app.js`).
2. Rebuild: `python3 build.py`
3. Check: `node test/test_sim.js && node test/test_cost.js && node test/test_cascade.js` (each exits non-zero if a check fails)
4. Publish: push this folder to the public repository that serves the page (GitHub Pages serves `index.html`).

Examples of one-line changes: a new default quota (`CONFIG.defaults.quota`), a new fitted model
(`CONFIG.models`), a new price control (`GROUPS`, then pass it through `compute()`).

## What is and is not modelled

Costs follow X's public price list and the assumptions in the left rail. Nothing has been tested on a
paid account. The model is static: a conversation is judged on its final size. The default quota and
monthly reply volume are placeholders.

## Public copy

The page is served at https://matthindman.github.io/reply-tree-collection-planner/ from the public
repository `reply-tree-collection-planner`, which holds a copy of this folder (without `planner.html`)
and the estimation code. To update it after a change here: run
`./sync_public.sh /path/to/reply-tree-collection-planner`, then commit and push in that checkout;
GitHub Pages redeploys in about a minute. Add `planner` or `estimation` as a second argument to copy
only that part.
